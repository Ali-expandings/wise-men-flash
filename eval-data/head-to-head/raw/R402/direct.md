Flat failure rate + rotating error messages across two years is itself the diagnosis. If these were independent bugs, fixing each one should shrink the pool and the rate should trend down over time. It hasn't. Something keeps generating new failure surfaces at the same pace you patch old ones — you're fixing symptoms, one exception type at a time, while the actual generator stays alive underneath.

Retries, alerting, and logging are all observability/mitigation layers. None of them touch the causal chain. Alerting tells you faster that it broke. Logging tells you more about how it broke. Retries only help when a failure is genuinely transient and resolves itself inside the retry window. None of that stops a new failure from showing up next month wearing a different exception.

Most likely mechanism for this exact pattern: the pipeline is triggered by clock time, not by upstream data actually being ready. It assumes at 2am (or whenever) that its inputs are complete. Most nights that's true. Some nights an upstream job runs long, a source lands partial, a schema shifts, a file arrives late — and the pipeline reads incomplete or malformed data anyway. Where it then breaks — a null somewhere, a join that explodes, a parse error, a timeout from scanning unexpected volume — depends on which stage first touches the bad data that particular night. Different stage, different-looking error, same root trigger. Someone reruns it hours later, upstream has finished by then, it passes — not because anyone fixed anything, because time passed.

Check this against the incident history: do failures correlate with a specific upstream job's completion time, month-end/DST/holiday boundaries, or a shared cluster being under load during the batch window? Does a rerun with zero code changes always eventually succeed? If yes, that's a data/dependency race, not a logic bug — and it explains why two years of patching individual exceptions hasn't moved the needle. The codebase has dozens of places an "upstream isn't ready" condition can surface as a distinct-looking crash; patching each one just moves the whack-a-mole hole.

Fix isn't more retries or better logging. It's making the pipeline dependency-aware instead of clock-aware: gate the run on an explicit completeness signal from upstream (success marker, row-count/freshness check, a sensor that polls until inputs are actually ready) instead of assuming readiness at a fixed time. Validate inputs at the boundary too — fail fast with one clear "upstream not ready" error at ingestion, instead of letting bad data propagate downstream to fail unpredictably wherever it happens to trip something.

Worth ruling out in parallel: resource contention (the nightly batch window is everyone's batch window — connection pool exhaustion, lock contention, cluster capacity) and genuine concurrency bugs (scheduler races, partial writes from a prior retry corrupting state for the next run). Same diagnostic test applies — check whether failures cluster around a shared resource or a specific upstream dependency's timing, rather than looking random.
