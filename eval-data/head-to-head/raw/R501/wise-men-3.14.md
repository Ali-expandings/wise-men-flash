## Recommendation

Turn on Postgres row-level security, but as a forced, fail-closed backstop layered underneath the ORM filter and lint rules you already have — not a replacement for them. Before you write a single policy, spend half a day tracing exactly which database role and connection the near-miss report ran through. That fact decides whether this fix even reaches the query pattern that almost caused the leak; everything else here is worth doing regardless, but it is not the whole fix until that path is accounted for.

## Why

A lint rule or a query wrapper can only prove that a filter is present in code it sees. It cannot prove the filter is correct, and it cannot see code it never runs through: a report script, a BI tool holding its own database credentials, a notebook, a backfill, an admin console, or an ORM code path that quietly skips the default scope (fetch-by-primary-key and relationship/association loading are common gaps in several ORMs — check your specific one's documented exceptions). A join that filters the parent table but not a child table, or a filter with an OR/precedence bug, also passes a check that only looks for "a filter exists." Any of these is a plausible shape for what nearly happened to you. Row-level security is enforced by Postgres itself on every statement a covered role runs, regardless of which tool or code path produced the SQL, so it closes exactly the class of gap that application-level checks structurally cannot see coming.

Your three worries are real, but each has a specific, well-documented cause and fix rather than being an inherent property of RLS:

Connection pooling is the one that can genuinely bite you, because it can turn a filtering bug into a new class of leak. Set the current customer with `set_config('app.customer_id', $1, true)` inside an explicit transaction — never with a plain session-level `SET`. The third argument scopes the value to the current transaction, so it is cleared automatically at commit or rollback. A session-level `SET`, by contrast, stays attached to the underlying server connection; under a pooler running in transaction-pooling mode (PgBouncer and similar), that connection is handed to the next client's transaction once yours commits, and whichever customer's request runs next silently inherits your customer ID. That is worse than today's bug, not better, so every code path that touches customer data needs to run inside an explicit transaction that sets the customer first.

Debugging gets easier, not harder, if you write the policy to fail loud. The common way to write an RLS policy (`customer_id = current_setting('app.customer_id')::bigint`) raises an error when no customer is set, which is what you want — never add a fallback that treats "unset" as "show everything," and don't silently swallow that error. Written this way, a missing-tenant bug turns into an immediate, loud failure instead of a wrong answer nobody notices; `EXPLAIN` also shows you the policy's condition directly on the query plan.

Performance surprises have a specific mechanism, not a vague one. A simple equality check on an indexed customer/tenant column is normally in the same cost class as the equivalent WHERE clause your ORM already adds — it typically folds into the same index scan. The real risk is narrower: Postgres will not push a condition below a row-security policy unless the function or operator involved is marked LEAKPROOF, so search-style predicates — ILIKE/trigram matching, full-text search, JSONB containment, and similar — can lose their index and fall back to scanning and filtering every row for that tenant. That is a real risk specifically for your heaviest queries if they lean on those operators, and it is measurable before you commit to anything: pull your top statements by execution time, check which functions and operators they use, and run `EXPLAIN (ANALYZE, BUFFERS)` with and without the policy in place for your largest customer.

None of this works if the connecting database role owns the tables, is a superuser, or has been granted the BYPASSRLS attribute — all three skip row-security silently, tests still pass, and everyone believes the fix is live. This is the single most common way teams end up with row-level security "on" that enforces nothing, and it is also where your actual near-miss most likely lives: an internal report is exactly the kind of workload that tends to run under a privileged connection, a BI tool, or a copy of the data (a materialized view or warehouse table, neither of which row-level security can protect, since policies apply only to ordinary tables). That is why the audit comes before the policy, not after.

One more scope limit worth naming plainly: row-level security enforces whatever tenant value it's given — it stops a missing filter, not a wrong one. If the tenant ID itself is set incorrectly (a bug that pairs the wrong customer's session with a request, for instance), or if SQL injection reaches far enough to call `set_config` directly, row-level security enforces that wrong value just as faithfully as a correct one. It's a backstop for the class of bug you just had, not a substitute for correct session-to-tenant binding or input validation upstream.

## What to do

First, today: find out which role and connection the near-miss report used, and whether that role owns the tables or holds BYPASSRLS or superuser. Check this by inspecting the report's code path and your role grants directly (`pg_roles` for `rolsuper`/`rolbypassrls`, `pg_class` for `relowner` against your customer tables). This takes hours, not days, and it is the fact that determines everything after it: if the report ran under a privileged or BI connection, or read a copy of the data, row-level security on your normal application role will not stop a repeat of this specific incident until that path is moved onto a tenant-scoped connection too — treat that as the first priority, ahead of the general rollout below.

In parallel, budget roughly an engineer-week for a cheap independent safety net that doesn't depend on which enforcement layer you pick: an assertion in whatever serves customer-facing reports and exports that every row's customer ID matches the requester's, failing loudly rather than shipping; one canary test tenant whose data appearing anywhere outside its own requests pages someone; and a single logged chokepoint that any raw SQL must go through, requiring an explicit tenant ID argument and logging the caller and row count. This is worth doing even if you were keeping app-layer checks only, because right now nothing would tell you if the near-miss had actually gone through — a human happened to notice.

Then, for the row-level security rollout itself: create a database role for the application that does not own the tables and does not have BYPASSRLS, separate from whatever role runs migrations. Starting with invoices and their child tables (add an indexed customer/tenant column to child tables if they don't already have one), enable and force row-level security with the single-equality policy above, and move the tenant-setting call into your ORM's transaction-start hook so it happens automatically rather than depending on every call site remembering it. Run your full test suite plus the top statements by execution time under the new role, with the policy active, against a staging copy sized like production. Budget roughly a week for that first slice on the highest-risk tables; a full rollout across every customer-scoped table is realistically several weeks more, mostly backfilling missing tenant columns and working through tables one at a time behind a flag (an internal test tenant first, then a small percentage of real ones, before the app's default connection role changes). Roll back at any stage by reverting the connection credentials — no schema change is required to undo it.

Stop and reassess, rather than pushing through, if either of two things turns up: a code path that genuinely cannot be wrapped in an explicit transaction before its first query runs (the tenant-setting mechanism itself would then become a new leak, and that path needs an application-level fix first), or a heaviest-query benchmark that shows real regression tied to non-leakproof operators that can't be rewritten — in that case, scope those specific queries out through a narrowly reviewed function rather than exempting a whole table or abandoning the policy.

## Risks of this plan

Row-level security enabled on a role that owns the tables, or that has BYPASSRLS, protects nothing while looking like it does — this is why the audit is the first step, not a footnote, and why it's worth an automated check (at CI time or application startup) rather than a one-time manual review, since a future migration script or "temporary" debugging connection can quietly reintroduce it. A tenant value set at session scope instead of transaction scope, under a pooler that recycles connections between different customers' requests, creates a leak class that does not exist in your system today — this has to be built and tested correctly from the start, against your actual pooler configuration, not assumed to work. Search-heavy queries that depend on operators Postgres won't push below the policy can regress for your largest customers specifically, which is exactly where you can least afford a surprise; benchmark before full rollout rather than after. And the plan's biggest risk isn't technical at all: treating "we turned on row-level security" as equivalent to "we fixed the incident" without ever confirming that the report which nearly leaked would actually run under the newly-enforced role — that would leave you with real confidence and no real protection on the one path that already came close to failing.

Waiting costs more than any of this. The application-layer status quo already produced one near-miss on real financial data, and every additional raw-SQL script, internal tool, or new hire is another chance for the same gap to go the other way before a fix lands — lint- and review-enforced rules are also the kind that tend to erode fastest exactly as a team and its tooling grow, which is a reason to move, not a reason to wait for a perfect rollout.

None of this is a one-way door. Because row-level security is added underneath your existing filter rather than instead of it, and rolled out table by table and tenant by tenant behind a flag, a mistake at any stage degrades back toward the app-layer-only posture you already have today, not past it — and it reverts with a credential or flag change, no schema rollback required. The one failure mode that doesn't revert cleanly is the confidence itself: believing the gap is closed without having checked that the exact path that almost failed now runs through it.

## Strongest counter-position

The strongest case against this plan doesn't dispute that row-level security works as described — it disputes that switching enforcement layers is the thing that would have stopped your near-miss, or would stop the next one. On this view, an internal report is exactly the workload that legitimately needs broader access, so whichever layer you pick, that workload tends to end up exempted from it: from row-level security by a BYPASSRLS grant or a table-owner connection, from the application check by a suppressed lint rule or a direct database connection. If that's right, the decision on the table is about the layer that would not have covered the query class that actually caused the scare, and the thing that actually saved you this time was a person noticing, not either control — nothing in the plan above would have paged anyone if that report had gone out, and nothing would let you reconstruct who saw what afterward. There's a sharper version of this objection too: moving enforcement into the database can make the exemption problem worse, not better, because a lint suppression sits in a diff someone can grep and a code reviewer can see, while a role-level bypass grant is invisible in application code and easy to forget once issued — under deadline pressure, the team that needs the exemption is exactly the team incentivized to take the durable, harder-to-notice one. Where this argument is weakest is that it is a claim about what your organization will do under pressure, not about what row-level security can technically do; if the reporting workload really does get rebuilt to run tenant-scoped rather than granted a standing bypass, the objection mostly collapses into "also build the detection layer," which this plan already includes for exactly that reason. It wins outright if the day-one audit shows the near-miss ran through a connection that can't realistically be brought under the tenant-scoped role — at that point, fixing that specific path outranks the general rollout, not the other way around.

## Confidence

High that a forced policy on a non-owner, non-bypass role closes the class of gap that a code-level filter structurally cannot see, and that the pooling and performance mechanisms described above (transaction-scoped settings vs. session-scoped ones under a pooler; LEAKPROOF and index pushdown for search-style operators) are accurately characterized — these are stable, well-documented properties of how Postgres and connection poolers behave, not a judgment call.

Medium on whether this plan, by itself, would have stopped the specific incident that prompted it. That rests on one fact nobody in this analysis has: which role, connection, and data source the near-miss report actually used. If it ran under the normal application path, row-level security closes it. If it ran under a privileged connection, a BI tool, or a copy of the data, it doesn't, until that path is separately addressed — which is exactly why finding that out is the first step above, not the rollout itself.

Medium on the time estimates — a first slice in about a week and full coverage in several more is a reasonable range for a system this size, but it depends on how many tables are missing tenant columns and how many code paths currently run outside an explicit transaction, neither of which is known yet.
