## Recommendation

Turn on row-level security as a second, fail-closed layer underneath the ORM filter and lint rule you already have, not as a replacement for them — but first spend a day confirming which database role and code path the near-miss report actually used, since that fact decides whether row-level security would even have caught it. In parallel, add a check on data leaving the system (verify every row's customer ID against the recipient before any customer-bound export or report is delivered), because that is the control neither option in your original framing provides, and it is the one most likely to have prevented this specific incident.

## Why

Row-level security and the application-level wrapper aren't actually substitutes for each other; they close different gaps, and the choice as posed hides that. The wrapper and lint rule are a static check on one code path: the ORM's query builder. They cannot see, and cannot enforce, anything that doesn't go through that path — raw SQL, a migration or backfill script, an admin screen, a BI tool, a read replica query. Row-level security is the opposite shape: Postgres attaches the tenant predicate directly to the table and applies it to any session using a role that doesn't own the table and doesn't have the BYPASSRLS attribute, regardless of what issued the query or whether anyone remembered to filter. That changes the failure mode from fail-open (miss the filter, get every row) to fail-closed (miss the tenant context, get zero rows). For a query that already filters by an indexed customer_id, adding the same predicate as a policy costs close to nothing: the session variable it checks is evaluated once per statement, not per row, so the plan looks like the one already running.

But row-level security only protects connections that go through a non-owner, non-bypass role with the tenant context correctly set — and that is not how most internal reporting, admin, and BI access is set up. Those tools typically run as the table owner, a privileged role, or against a replica precisely because they need to see across customers; a materialized view can't carry a policy at all, and refresh jobs run as whatever role owns the view. An internal report that nearly showed one customer another customer's invoices fits that profile at least as well as it fits a forgotten ORM filter. If that's what happened here, turning on row-level security for the application's own database role fixes a real gap but does not fix the one that almost leaked — and worse, "the database now enforces isolation" tends to become the official answer, which quietly lowers scrutiny on exactly the privileged paths that still bypass it.

The three worries about row-level security are all addressable and are mostly about one implementation detail: how the tenant is set on a pooled connection. Set it session-wide with a plain SET and, under a transaction-mode pooler, it can persist on the physical connection after your code releases it and apply to the next customer's transaction — a real failure mode, not a hypothetical one (the same class of bug behind a well-known 2023 incident where a caching/connection-reuse defect briefly exposed one user's chat data to another). Set it with SET LOCAL as the first statement inside an explicit transaction instead, and Postgres discards it at commit or rollback before the connection goes back to the pool — correct by construction, no pooler configuration required. That single rule (never a bare SET, always SET LOCAL inside a transaction you control) is what makes pooling safe. Debugging gets harder only if failures stay silent; a missing tenant context should raise an error, not return an empty result set that looks like success. Performance holds up as long as the policy stays a plain indexed equality; it degrades when a policy calls a function per row, or when a query relies on an operator Postgres hasn't marked leakproof — pattern-matching search is the common case — because those can't always be safely pushed below the security check, which costs you an index. That's worth benchmarking on your actual heaviest queries before a broad rollout, not assuming away.

## What to do

1. This week: pull the logs for the near-miss report and determine what database role it ran as, and whether it went through the ORM, raw SQL on the app's connection, or a separate reporting/admin/BI credential. This is the fact that decides everything below.

2. If it ran on the application's own role (ORM or raw SQL on that connection): this is the case row-level security directly closes. Roll it out to the invoices table first — the one involved — behind a database role that does not own the tables, with FORCE ROW LEVEL SECURITY set, SET LOCAL issued as the first statement of every transaction from one centralized connection-acquisition hook (not scattered per call site), and a policy that raises an error rather than silently returning nothing when no tenant is set. Keep the ORM filter and lint rule exactly as they are as the first line of defense. Roughly a week to prototype and benchmark, another one to two to harden and ship the invoices table behind a flag with a two-tenant isolation test in CI, then four to eight weeks to extend to the rest of the customer-scoped schema table by table.

3. Regardless of what step 1 finds: add a check on the way out, not just on the way in. Before any customer-bound export, report, PDF, or email leaves the system, verify every row's customer ID against the recipient's, with the expected ID sourced from who's receiving it, not from the report's own parameters. This is the control that covers reporting, admin, and BI paths no matter what role they run as, and it's the one gap neither option in the original framing closes. Start with the exact report path involved in the near-miss; a few days to two weeks depending on how many delivery channels exist.

4. Stop-ship condition: benchmark your heaviest twenty or so queries, run as your largest customer, before extending row-level security past the invoices table. If more than a handful regress materially at p95 once policies are reduced to plain indexed equality, stop the broad rollout, keep row-level security scoped to the tables that need it most, and lean on the app-level wrapper for the rest.

## Risks of this plan

Rolling out row-level security costs real weeks, and it adds a new silent-failure mode (empty results instead of errors) if the error-on-missing-context rule isn't enforced everywhere from day one — that would make debugging worse, not better, exactly the worry that motivated caution here. It also does nothing by itself for any connection that already runs as a privileged or owning role, which is a common shape for exactly the reporting and admin tools most likely to have caused this incident; shipping it can create false confidence that the isolation problem is solved while the actual leaking path stays open.

Not doing it, or waiting on it, costs differently: every new raw-SQL query, script, admin tool, or future service is another chance to reproduce this same near-miss, with the same blast radius, and nothing about the current design structurally prevents that — it only makes it a matter of discipline and code review, which is exactly what almost failed once already.

This is a reversible plan. Row-level security can be added table by table behind a role and a flag, and rolled back per table if it regresses a job or a query without touching the tables not yet migrated; the application-level filter keeps working throughout, so nothing about this rollout removes the safety net you already have. The one path that isn't easily undone is skipping the delivery-side check and having a second near-miss reach an actual customer before the root cause of the first one is confirmed.

## Strongest counter-position

The case against making row-level security the centerpiece of the response: internal reports and admin tools "legitimately read across customers, so they normally run as something RLS skips: the table owner, a role with BYPASSRLS, a superuser psql session, a read replica, a BI tool, or a materialized view refreshed by a privileged job" — none of which row-level security constrains. On that reading, turning it on "would put a second lock on the customer-facing ORM path, which already filters every query, and leave the path that nearly leaked exempt." The organizational risk compounds it: once "the database enforces isolation" is the official answer, review of missing filters tends to relax on exactly the bypassed paths, so the two layers fail together instead of independently.

This wins outright if the near-miss query ran under a role row-level security wouldn't apply to — the more likely case for something described as an internal report. In that world, the entire rollout, however well executed, would not have prevented the incident that prompted this question, and the delivery-side check in step 3 is doing the real work. It loses force if the report instead ran on the application's own database role, through the ORM or raw SQL on that same connection — the case row-level security was built for — which is exactly why step 1 checks this before step 2 commits any engineering time.

## Confidence

High on the mechanics: that a bare SET can leak a tenant across a transaction-mode pooled connection while SET LOCAL inside an explicit transaction cannot, that table owners and BYPASSRLS roles bypass policies entirely, and that a plain indexed-equality policy is close to free on a query that already filters the same way — these follow from documented Postgres and connection-pooler behavior, not from any one team's experience.

Medium on cost and performance at this scale: the week-to-two-month estimates and the roughly-20%-regression stop-ship threshold are reasonable starting points, not measured numbers for this schema or query mix, and should move once the heaviest queries are actually benchmarked.

Low, and the thing to resolve first: whether row-level security would have caught this specific near-miss at all. That depends entirely on which role and code path the report ran under, which isn't yet known — it's the first thing to check, not an assumption to build the rest of the plan on.
