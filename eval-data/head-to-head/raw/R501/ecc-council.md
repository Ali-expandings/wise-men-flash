## Council: RLS vs. Application-Layer Tenant Isolation

**Architect:** Turn on row-level security as a mandatory backstop layered under the existing ORM filter and lint rules, starting with invoices — not an either/or swap.
App-code enforcement is fail-open (anything outside the linted pipeline is unprotected); RLS is fail-closed at the data layer, which is exactly the gap the near-miss exposed.

**Skeptic:** Enable RLS on the sensitive tables first, layered under current enforcement, not flipped on schema-wide on day one.
Pooling/performance/debugging fears are overstated for the common case, but blanket RLS will collide with legitimate internal cross-tenant reporting needs and create pressure for a bypass role that quietly recreates the hole.

**Pragmatist:** Ship the lint wrapper now, land table-by-table RLS within weeks — additive, not a rewrite.
Pooling, performance, and debugging objections are solved patterns (`SET LOCAL` per transaction, an indexed `customer_id`, a day spent learning the silent-empty-result failure mode), so none of them justify delay.

**Critic:** RLS should become the mandatory enforced layer, with app-code checks demoted to a secondary gate, not the reverse.
The near-miss already proved app-only enforcement is structurally blind to direct-SQL paths; the live danger now is implementing RLS wrong — session-level `SET` instead of transaction-scoped `SET LOCAL` under PgBouncer transaction pooling leaks one tenant's context into the next request — or leaving the reporting role as `BYPASSRLS`/table-owner, which makes RLS a no-op on exactly the path that already leaked.

### Verdict
- **Consensus:** All four voices back turning on RLS, at minimum on financial tables like invoices, layered with — not instead of — the app-layer wrapper and lint rules. All three subagents independently treated the named objections as solved implementation details rather than reasons to hold off: use `SET LOCAL` inside an explicit transaction (never session-level `SET`) for PgBouncer transaction-mode pooling safety, keep `customer_id` indexed so policy predicates stay cheap, and roll out per-table starting with invoices instead of schema-wide.
- **Strongest dissent:** Two linked tensions, not a clean split. First, how central RLS should be — the Critic wants it promoted to primary enforcement with lint as secondary, while Skeptic/Pragmatist/Architect keep the app layer primary with RLS as backstop; in practice this doesn't change what ships, only which layer you trust more. Second, and more substantive: the Skeptic flags that the reporting path behind the near-miss likely needs legitimate cross-tenant access, which strict RLS breaks — while the Critic independently warns that if that same reporting role already has `BYPASSRLS` or owns the tables, RLS silently does nothing for it. Together these point at one unresolved design question the original framing skips: legitimate internal cross-tenant reporting needs its own deliberately scoped, audited path, not an ad hoc bypass and not an assumption that RLS automatically covers it.
- **Premise check:** Yes. The question frames RLS and app-code enforcement as alternatives; all three subagents rejected that framing — the real choice is RLS-as-backstop now vs. never closing the raw-SQL gap that already nearly caused a breach. No voice found a simpler mechanism that closes that specific gap; the closest thing to a "simplest alternative" was the Skeptic's scoped rollout (financial tables first) rather than a schema-wide flip.
- **Recommendation:** Turn on RLS, starting with invoices and other financial tables, as a mandatory backstop under the existing ORM filter and lint rules — keep both. Before enforcing: (1) audit every DB role touching these tables (app, migrations, the reporting tool, admin scripts) for `BYPASSRLS` or ownership, either of which silently defeats RLS, and add `FORCE ROW LEVEL SECURITY` wherever the app connects as owner; (2) verify every request path sets tenant context via `SET LOCAL` inside an explicit transaction, never session-level `SET` — get this wrong under connection pooling and you introduce a worse, silent cross-tenant bug than the one you're fixing; (3) benchmark the heaviest queries against an indexed `customer_id` policy predicate before rolling out broadly; (4) build a deliberate, separately-audited path for legitimate cross-tenant internal reporting instead of leaving it as an implicit bypass. What changes the answer: if the app can't currently guarantee one transaction per request, fix that plumbing first — RLS on unreliable session handling can fail in a new, harder-to-spot way. If there's near-term compliance pressure (SOC 2, enterprise security reviews), that argues for accelerating RLS rather than waiting, since "enforced by lint convention" is a weak answer in an audit.
