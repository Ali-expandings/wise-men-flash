## Recommendation

Turn on row-level security, but as a backstop under your existing app-layer filter, not a replacement for it — enable and FORCE row-level security on every tenant table, keep the ORM's automatic customer_id filter and the wrapper/lint rule as your everyday enforcement path, and let RLS catch everything the wrapper structurally can't see.

## Why

- **All three reviewers independently converged on the hybrid**, arguing from different angles (Postgres internals, rollout/ops, adversarial stress-test) — that convergence from different starting points is stronger signal than any one report alone, and none of them landed on "app-layer alone is fine."
- **The wrapper+lint plan almost certainly wouldn't have stopped the incident you're reacting to.** Lint only sees code that's in your repo and goes through your query builder. "An internal report" nearly leaking invoices reads like a BI tool, analyst script, or direct-SQL report running outside the ORM entirely — exactly the class of access a linter can't inspect, because it never touches your codebase. If that's what happened, hardening the wrapper fixes a different bug than the one that almost bit you. Confirm this fact before you finalize anything — it changes how urgent RLS actually is.
- **The real case for RLS isn't "sturdier," it's fail-closed vs. fail-open.** Today, a missed filter returns every tenant's rows — the worst possible failure. With RLS enabled and FORCED (`FORCE ROW LEVEL SECURITY`, so even your app's table-owner role is bound by policy, not just other roles), a missed or misconfigured tenant context typically returns zero rows or errors, not another customer's data. That flip — from "silently leaks everything" to "silently leaks nothing, breaks loudly instead" — is what actually addresses the failure mode that scared you, and no amount of lint changes what a raw-SQL or out-of-band query does at runtime.
- **Your three concerns are real, but each has a known, specific answer — not a reason to avoid RLS:**
  - *Connection pooling:* the failure mode is real and well-documented — a bare `SET app.current_customer_id = ...` under PgBouncer transaction-mode pooling can leak onto the next tenant's transaction when the connection is reused. The fix is equally specific: scope tenant context with `SET LOCAL` (or `set_config(key, value, true)`) inside the same transaction as the query, never a session-level `SET`. Done that way it reverts automatically at COMMIT/ROLLBACK regardless of pooling mode. Put this in the same middleware chokepoint that already sets ORM tenant context, so it's one code path, not 2,000.
  - *Harder debugging:* also real, but bounded and front-loaded rather than open-ended. The new failure signature is "unexpected empty result," not "wrong data" — so the fix is procedural: use `current_setting('app.setting', false)` (strict mode) so a missing tenant context errors instead of silently returning nothing, add `pg_policies` / `SHOW app.current_customer_id` to your on-call runbook, and add a CI check asserting every tenant table has `relrowsecurity`/`relforcerowsecurity` set. One-time tooling cost, not a per-incident tax.
  - *Performance:* negligible in the common case — a policy that's just `customer_id = current_setting(...)::int` on an indexed column duplicates a predicate your ORM already sends, and Postgres typically folds it into the same index scan. It gets expensive specifically when the policy involves a join or subquery instead of a plain column check; the query relies on non-leakproof operators (full-text `@@`, jsonb `@>`, trigram `LIKE`) where the planner won't push them ahead of the security qual, silently killing index usage; or you're aggregating over very large scans where per-row policy evaluation adds up. Before enabling, run `EXPLAIN (ANALYZE, BUFFERS)` on your actual heaviest queries against a production-scale copy — that tells you which of these apply to you instead of guessing.

## Tradeoffs and risks

- **RLS is not a checkbox — misconfiguration fails open, silently.** Table owner without FORCE, an app role with BYPASSRLS, a new table that ships without ENABLE, a later "support staff" policy that ORs in broader access, a view or SECURITY DEFINER function owned by a bypassing role — any of these quietly reopens the hole RLS was supposed to close, with nothing telling you it happened. Mitigate with catalog-level CI checks, not manual review.
- **Migrations, background jobs, and admin scripts need their own explicit design**, not an implicit exemption — give them a separate, audited role rather than letting them bypass RLS as a side effect of running as the table owner. That's the same category of access that produced the original incident (an unmanaged, direct path to the data) — don't recreate it for "trusted" internal tooling.
- **RLS doesn't fully cover foreign-key and uniqueness checks** — those can let one tenant probe for the existence of another tenant's rows even with policies in place. Composite keys that include customer_id on child tables reduce this; it's a residual risk to know about, not a blocker.
- **Hybrid has a real cost: two enforcement layers to maintain and test, not one.** One reviewer pushed back hard here — testing the cross-product of app-layer and RLS across pooling modes, background jobs, and access paths is genuinely more work than either layer alone, and a half-done hybrid can be worse than one well-executed layer. Budget it as real project scope, not a weekend toggle.
- **What would flip this recommendation:** if your architecture genuinely cannot guarantee every tenant-scoped query runs inside an explicit transaction (so `SET LOCAL` has nothing reliable to scope to), fix that first — RLS on top of it will be flaky in a way that's hard to distinguish from random bugs. And if "2,000 business customers" is actually a much smaller number of large, high-compliance tenants, database- or schema-per-tenant may be worth a separate look — but at 2,000 tenants, shared-schema-plus-RLS is the standard answer, not a stopgap.

## Final call

Do now: enable + FORCE RLS on tenant tables behind a `SET LOCAL`-per-transaction wrapper (reuse your existing tenant-context middleware), keep the ORM filter and lint rule as-is, and add CI catalog checks (RLS enabled+forced on every tenant table, app role not BYPASSRLS) so a misconfiguration fails the build instead of failing open. Before writing a single policy, confirm how the near-miss report actually connected to the database — that answer tells you whether RLS closes the real gap or a hypothetical one. Roll out table-by-table starting with your lowest-risk table, using shadow/canary comparison against current app-layer results, and run EXPLAIN ANALYZE on your heaviest queries first so performance surprises show up in staging, not production.

Later, once the above is stable: tighten policies to `RESTRICTIVE` (not `PERMISSIVE`) so no future policy can silently widen access, and revisit BI/reporting tool access as its own audited, scoped role rather than an ambient exemption.
