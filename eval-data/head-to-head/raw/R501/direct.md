**Pick RLS — but as an added layer, not a replacement for what you have.**

The near-miss already tells you where the app-layer approach fails: it was an *internal report* that nearly crossed tenants, not a bug in ORM-generated code. A query wrapper and lint rule only protect the code path that runs through your CI pipeline. They don't protect ad hoc scripts, BI tools (Metabase/Looker/whatever), a read replica someone connects to with psql, migrations, admin tooling, or the next internal service that talks to this database without importing your lint config. That's exactly the gap the incident found. A lint rule is pattern-matching against source text — it can be defeated by dynamic SQL, string-built queries, views, or just not running in that repo. RLS moves the check into the data itself, so it holds regardless of what's issuing the query. After an incident caused by an unanticipated access path, that invariance is the property you actually want.

Keep the ORM auto-scoping and the lint rule. They're cheap, they give fast feedback in code review, and they keep the common-case queries efficient and correct. RLS becomes the backstop that's true even when those are wrong, bypassed, or simply not in the loop — defense in depth, not a swap.

On your three specific worries:

**Connection pooling.** This is the one real landmine, but it's a solved problem, not a reason to avoid RLS. The failure mode is using session-level `SET` with a pooler in transaction mode (PgBouncer), where a connection can get reused across different logical requests without resetting state. The fix is to always scope the tenant setting to the transaction with `SET LOCAL` (or `set_config(name, value, true)` — the `true` means local), issued inside the same transaction as the query. That's the standard pattern for RLS-based multi-tenancy and it composes fine with transaction-mode pooling. Also make the policy fail *closed*: `current_setting('app.tenant_id', true)` returns NULL if unset rather than erroring, and `customer_id = NULL` is never true, so a request that forgets to set the tenant context returns zero rows, not all rows. Test that explicitly before rollout — it's the difference between "worst case, a bug breaks a customer's report" and "worst case, a bug leaks data," which is the whole point.

**Debugging.** Harder mainly if you debug as a superuser or table owner, since RLS is invisible to those roles by default — you can "fix" something locally that doesn't reproduce because you unknowingly bypassed the policy. Two mitigations: run `ALTER TABLE ... FORCE ROW LEVEL SECURITY` so it applies even to the owner, and make sure your app's connection role doesn't have `BYPASSRLS`. Debug using the same restricted role production uses, not a privileged one.

**Performance.** A policy like `customer_id = current_setting('app.tenant_id', true)::uuid` is just another indexed predicate — and you already need `customer_id` indexed today, since the ORM is filtering on it on every query. Postgres pushes the policy qual into the plan alongside your other WHERE clauses; it composes with existing indexes rather than adding a separate filter pass. The real risks are non-obvious ones: a policy that calls a non-`STABLE` function gets re-evaluated per row instead of once; joins across multiple RLS-protected tables each add a predicate, which can matter on your heaviest queries; and if any table is partitioned, verify RLS doesn't interfere with partition pruning. So don't take this on faith — pull your top 10-20 heaviest/slowest queries, run them against prod-scale data with RLS enabled in a staging environment, and compare plans before flipping it on broadly. This is exactly the kind of thing worth measuring, not guessing at.

Rollout I'd actually do: enable RLS table-by-table, starting with `invoices` since that's what almost leaked. Keep one narrowly-scoped, audited "admin" role for legitimate cross-tenant operations (support tooling, billing reconciliation) rather than leaving every query capable of seeing everything by default. Load-test the heavy queries before each table goes live. Leave the lint rule running the whole time.

**What would change my answer:**

- If you profile your actual heaviest queries at real data volume (watch for skewed tenants with much larger row counts) and find a regression that indexing/partitioning genuinely can't fix, I'd scope RLS to the higher-risk tables only rather than blanket-applying it, and treat the rest as a longer-term project.
- If you're not on real Postgres — a compatible-but-limited managed service — verify its RLS support and planner behavior match vanilla Postgres before betting on it; some don't push policy quals as well.
- If it turns out the near-miss query actually did run through ORM-covered application code (i.e., it was raw SQL sitting in your repo, not an out-of-band report or script), the gap is narrower than I'm assuming, and tightening CI enforcement buys you more than I'd otherwise credit it. I'd still lean RLS given 2000 tenants and invoice data, but the urgency shifts.
- If you're heading toward a compliance review (SOC 2, enterprise security questionnaires), that pushes further toward RLS, not away — "is tenant isolation enforced at the database layer or only in application code" is a standard question, and app-only isolation is a known red flag in vendor reviews.
- 2000 tenants in one database is squarely RLS's comfort zone — it's not a scale where you'd need schema-per-tenant or database-per-tenant instead. If you were looking at tens of thousands of tenants with hard contractual isolation requirements, that's a different conversation; you're not there.
