## Postgres FTS vs. dedicated search cluster for ~4M docs

**The "relevance gets bad at scale" claim needs unpacking, because it's not really about document count.** Postgres's GIN index finds matching rows efficiently even at 4M+ documents — that part scales fine and plenty of teams run Postgres FTS well past this size. What actually degrades is the *ranking* step: `ts_rank`/`ts_rank_cd` is roughly term-frequency based, with no real IDF term and no BM25-style document-length normalization, so it doesn't naturally downweight common words the way Lucene-based engines do. Worse, Postgres computes rank at query time over every row the GIN scan returns, rather than using a top-k pruning algorithm (WAND, block-max WAND) that lets Lucene stop early. So the failure mode isn't "4M rows is too many" — it's "queries containing common terms return huge candidate sets that all have to be scored before sorting," and that gets slower as the corpus grows. Deep pagination (OFFSET-based) on ranked results has the same problem. If your queries are reasonably selective and you're not doing deep pagination, this may just not bite you at this size.

**Team fit is the bigger factor here, and it points hard at Postgres.** Running Elasticsearch or OpenSearch isn't a one-time setup cost — it's ongoing: shard/replica sizing, cluster health and split-brain scenarios, mapping migrations, version upgrades (historically painful), heap tuning, security hardening, backup/restore, capacity planning, monitoring. For a team of five with zero prior experience, that's effectively asking someone to become a part-time search-cluster operator, with real on-call risk while they're learning. That cost is largely independent of your document count.

**Drift risk doesn't go away even with a managed service.** Any external index — self-hosted or hosted — needs a sync mechanism (CDC via logical replication/Debezium, outbox pattern, or dual writes) to stay consistent with Postgres. Dual writes drift; CDC is more robust but is itself a piece of infrastructure you build and maintain. Budget for this regardless of which path you pick.

This isn't actually a binary choice — there's a spectrum worth knowing about:

- **Postgres native FTS + pg_trgm** (for typo tolerance) — simplest, no second system, weaker relevance quality, tunable via field weights (`setweight`).
- **ParadeDB / pg_search** — a Postgres extension that adds BM25 scoring (via Tantivy, a Rust Lucene-like engine) inside Postgres itself. Directly targets the relevance gap without adding a second system. Newer project — check current maturity/production track record before betting on it.
- **Managed search** (Elastic Cloud, AWS OpenSearch Service, Algolia, Typesense/Meilisearch Cloud) — gets you real BM25 relevance without your team operating cluster internals. Directly solves "nobody's run a cluster before" by paying someone else to. Still has the drift/sync problem, plus vendor cost and lock-in.
- **Self-hosted lightweight engine** (Typesense, Meilisearch) — meaningfully simpler ops than Elasticsearch/OpenSearch (single binary, simple mental model, good relevance defaults), can run as one node plus a replica at this scale without full "cluster" complexity. Still a second system to sync and operate.
- **Self-hosted Elasticsearch/OpenSearch cluster** — most capable and flexible, but the highest ops burden — the worst fit for this team's experience level.

**Recommendation:** default to Postgres first. Build the `tsvector` column (generated column + GIN index), weight fields, add `pg_trgm`, and — critically — test it against a real or realistic copy of your 4M docs using your actual worst-case queries (your most common terms, plus whatever deep-pagination patterns you need). Measure p95 latency and eyeball whether the top 10 results look right. That gives you real numbers instead of folklore. If testing shows a genuine relevance or latency problem, escalate in order: try ParadeDB before leaving Postgres, then a managed search service before self-hosting a cluster. Self-hosted Elasticsearch/OpenSearch should be the last resort given your team's profile, not the default alternative.
