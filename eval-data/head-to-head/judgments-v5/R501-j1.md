**PASS 0: Errors**

**A**
- The Confidence section cites a "roughly-20%-regression stop-ship threshold" that the plan never states. Step 4 says only "more than a handful regress materially."
- It lists "a read replica" among paths RLS skips. Physical replicas carry the same policies, so the bypass comes from the role, not the replica.
- "Evaluated once per statement, not per row" is only true when the policy predicate is used as an index condition. When it is applied as a filter, a STABLE call runs per row.

**B**
- It states as fact that the near-miss was "not a bug in ORM-generated code" and was "exactly the gap the incident found." That is an inference (hedged later).
- It says RLS "holds regardless of what's issuing the query" and lists BI tools, psql on a replica, migrations and admin tooling as covered. Owner, superuser and BYPASSRLS roles, which those tools commonly use, skip RLS. The audited admin role B recommends reopens that gap.
- It says `current_setting(..., true)` "returns NULL if unset." On a pooled connection that previously ran SET LOCAL, it returns '' and the `::uuid` cast raises an error.
- "App-only isolation is a known red flag in vendor reviews" is overstated.
- It implies STABLE functions are evaluated once rather than per row. That holds only when the predicate is used as an index condition.

**C**
- It says strict `current_setting()` raises "if the setting was never bound in that transaction." On a reused pooled connection the value stays defined as '', and only the `::int` cast raises.
- "Something already got in through a path the lint rule didn't cover." The lint rule is only proposed and doesn't exist yet. The incident shows a gap in the ORM filter, not in the lint rule.
- "Almost certainly a path outside the ORM-mediated, lint-checked application code" overstates what "internal report" supports.

**D**
- "The near-miss was raw SQL" is stated as fact. The question implies it but doesn't say it.
- It says RLS is the only control that "a raw SQL query cannot route around by construction." Owner, superuser and BYPASSRLS sessions do route around it, which D itself concedes later.
- It calls the app-code option "a description of the control that already exists and already failed." The wrapper and lint rule are new, and the existing control nearly failed rather than failed.
- It treats advisor unanimity as "the strongest data point." Agreement among advisors is not evidence about how Postgres behaves.
- It says isolation doesn't travel through replication. Physical replicas keep the policies; only logical copies and ETL lose them.

**E**
- "Roll back at any stage by reverting the connection credentials — no schema change." With FORCE ROW LEVEL SECURITY on, as the plan specifies, a table-owner role is still bound by the policies. Only a superuser or BYPASSRLS role escapes, so the rollback lever fails in the common case where the app connects as the owner.
- "Debugging gets easier, not harder" is overstated.

**F**
- The recommended path rests on a "shadow/audit mode — policies attached and logging what they would have denied, without FORCE." Postgres has no such mode. ENABLE enforces immediately for non-owner roles, FORCE only adds the owner, and RLS logs no denials. **Material.**
- It says `current_setting()` in a policy is "opaque to the planner's selectivity estimates" in a way a plain WHERE isn't. The planner folds stable functions when estimating, and parameterized ORM queries hit the same generic-plan limits. The synthesis still treats this as a conceded standing cost.
- It treats one council member's personal RLS experience as answering whether "this team" has it, and the synthesis reports that as resolved "yes."
- "If SET LOCAL isn't reapplied on every checkout, you … leak rows." A transaction-scoped setting cannot leak across checkouts.
- It frames the rollout as flipping FORCE "on 2,000 live tenants." FORCE is set per table and only affects the owner.

**G**
- "RLS fails silently — missing GUC returns zero rows, not an error," with a test asserting zero rows. That is false for G's own strict `current_setting(...)::uuid` policy, which raises an error. **Material:** it misinforms on one of the asker's three worries.
- It says RLS would have prevented the incident "regardless of what issued the query," naming migration scripts and psql sessions. Privileged roles bypass RLS, and G itself reserves owner/superuser for migrations.
- "At 2,000 tenants you're almost certainly running PgBouncer in transaction mode" is overstated; tenant count doesn't determine pooling mode.
- The debug snippet runs `SET LOCAL` outside a transaction block, where it has no effect.
- "Here's why it's not close" is overstated given that the report path is unknown.

**H**
- "Tighten policies to RESTRICTIVE (not PERMISSIVE)." With only restrictive policies, no rows are visible, so the advice as worded locks out all access.
- "A missed or misconfigured tenant context typically returns zero rows or errors." A wrong tenant value returns that tenant's rows; this only holds for a missing value.
- It cites its own sub-reviewers' agreement as "stronger signal," a mild appeal to internal consensus.

**I**
- It frames the alternative as "never closing the raw-SQL gap." That's a false dichotomy: the proposed lint rule would catch raw SQL in the repo.
- "The near-miss already proved app-only enforcement is structurally blind to direct-SQL paths" is overstated; "suggests" is the honest word.
