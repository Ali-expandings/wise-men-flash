**PASS 0 — Errors**

**A**
- It states as fact that the near-miss was "not a bug in ORM-generated code" and "exactly the gap the incident found". The question doesn't establish that the report ran outside the repo or CI. The "what would change" section hedges this later.
- It says RLS "holds regardless of what's issuing the query" and implies RLS covers BI tools, ad hoc psql, migrations and admin tooling. Superuser, BYPASSRLS and table-owner (without FORCE) roles bypass RLS, and those are the roles such tools usually use. This is material because it implies RLS closes the incident path without checking which role the report used.
- It says `current_setting(..., true)` "returns NULL if unset". On a reused pooled connection it returns '' instead, so the `::uuid` cast errors rather than returning zero rows. This is a minor mechanism slip; the policy still fails closed.
- "App-only isolation is a known red flag in vendor reviews" and "some [services] don't push policy quals as well" are overstated or unsupported.

**B**

- "Roll back… by reverting the connection credentials — no schema change is required" is wrong if the tables are FORCE'd and the old role is a non-superuser owner. Rollback would then need ALTER TABLE … NO FORCE or DISABLE.
- "Debugging gets easier, not harder" is overstated. Failing loudly helps with missing-context bugs, but RLS still adds hidden predicates and behaviour that depends on the role.

**C**
- "The wrapper+lint plan almost certainly wouldn't have stopped the incident" is overstated: raw SQL inside the repo would be caught by lint. It is partly hedged afterwards.

- It treats agreement among same-model reviewers as a strong independent signal, which overstates its weight as evidence.

**E**

- "The near-miss was raw SQL" is presented as established fact when it is an inference.
- It says RLS on the primary won't cover a report run against a replica. Physical streaming replicas carry the same policies; only a bypassing role or a logical/warehouse copy escapes them.
